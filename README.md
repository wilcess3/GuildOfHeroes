##### (Практическая работа №6) Шаг 12

**1. Какое состояние вашего объекта меняет TryFinish и почему не раньше:**
Метод TryFinish вызывает метод Sell(1) у объекта Product, что уменьшает его количество (Quantity). Это происходит именно на этапе завершения, а не на этапе старта, потому что TryStart выполняет только роль проверки и «бронирования». Если бы списание происходило сразу при старте, то в случае отмены операции товар был бы потерян. Физическое изменение состояния должно происходить только после успешного подтверждения операции

**2. Что произойдёт, если в TryStart по ошибке создать копию объекта:**
Если вместо сохранения ссылки (ProductToSell = product) создать копию (new Product(...)), то при вызове TryFinish метод Sell(1) изменит количество у копии, а не у оригинала. В результате операция завершится успешно, но в магазине (в контейнере Store) остаток товара не изменится. Именно поэтому в TryStart так важно сохранять ссылку на объект, чтобы методы работали с оригиналом в памяти

##### (Практическая работа №7) Шаг 14
* Таблица переходов операции:

| Исходное состояние | TryStart (Старт) | TryFinish (Завершение) | TryCancel (Отмена) |
| :--- | :--- | :--- | :--- |
| **Open** (Создана) | → **Active** | Отказ | → **Cancelled** |
| **Active** (В работе) | Отказ | → **Finished** | → **Cancelled** |
| **Finished** (Завершена) | Отказ | Отказ | Отказ |
| **Cancelled** (Отменена) | Отказ | Отказ | Отказ |

* Какие состояния вашей операции конечные:**
Конечными состояниями являются **Finished**  и **Cancelled** . Из них не выходит ни одна стрелка, потому что операция уже закрыта. Если попытаться вызвать любое действие (старт, завершение или отмену) для операции в конечном состоянии, программа вернет False

* Почему занятость вычисляется, а не хранится:**
Занятость не хранится в самом товаре (в классе Product нет поля IsBusy). Вместо этого метод IsProductBusy в классе Store каждый раз проверяет список всех операций: если есть хоть одна операция в состоянии Active, которая ссылается на этот товар, значит, товар занят
Это нужно для того, чтобы данные не рассинхронизировались. Если бы мы хранили флаг занятости в товаре, при отмене операции нам пришлось бы вручную его сбрасывать. А при вычислении — отменили операцию, и товар автоматически стал свободным, так как активных операций для него больше нет

2. **Чем отличаются get, set и private set:**

- get — позволяет читать значение свойства из любого места программы.
- set — позволяет записывать значение свойства из любого места программы (делает свойство полностью открытым)
- private set — разрешает записывать значение только коду, который находится внутри того же класса (например, методам или конструктору)

3. **Где проверяется начальное здоровье:**
   Начальное здоровье проверяется в конструкторе Hero(). Сначала задается и ограничивается рамками (от 1 до 200) значение MaxHealth. Затем проверяется Health: он не может быть меньше 0 и не может превышать MaxHealth

4. **Как Heal сохраняет границу MaxHealth:**
   В методе Heal сначала считается нехватка здоровья (missingHealth = MaxHealth - Health). Если запрошенное лечение больше или равно этой нехватке, здоровье устанавливается ровно в MaxHealth. В противном случае лечение просто прибавляется к текущему здоровью

5. **Как Name использует поле \_name и значение value:**
   Свойство Name работает с закрытым полем \_name. При попытке присвоить имя, в невидимую переменную value попадает переданная строка. Внутри set значение value проверяется на пустоту и очищается от пробелов с помощью Trim(), и только потом сохраняется в \_name

6. **Почему в конструкторе используется Name = name:**
   Строка Name = name; обращается к свойству Name. Так как конструктор находится внутри класса Hero, он имеет доступ к private set. Это запускает все проверки (на пустоту и обрезку пробелов), написанные в сеттере. Если бы мы написали \_name = name, проверки были бы обойдены.

##### шаг 14

1. **Почему два признака bool хуже одного перечисления?**
Два независимых признака (например, IsCompleted и IsCancelled) допускают невозможные состояния (когда квест одновременно и выполнен, и отменен). Перечисление QuestStatus имеет строго заданный список взаимоисключающих состояний, что защищает программу от логических ошибок

2. **Какие состояния поручения конечные и почему?**
Completed и Cancelled. Из них нельзя перейти в другие состояния, так как дело уже закрыто — либо успешно завершено, либо отменено

3. **Куда делась проверка AssignedHero != null в Quest.TryAssign?**
Она стала не нужна. Метод начинается с проверки Status != QuestStatus.Open. В состоянии Open исполнителя по определению быть не может (его ставит только сам метод TryAssign). Проверка статуса заменила собой проверку на null

4. **Где хранится занятость героя?**
Нигде не хранится. Она **вычисляется** методом IsAssigned на доске поручений (поиск активного квеста со статусом Assigned для конкретного героя)

5. **Почему проверку занятости нельзя делать после назначения?**
Если вызвать quest.TryAssign(hero), он изменит статус квеста и запишет исполнителя. Последующая проверка IsAssigned найдет этого же героя занятым на этом же квесте и вернет false, хотя изменение уже произошло (доска ответит «отказ», но данные испортятся). Проверять нужно строго до изменения

6. **Почему доска не даёт удалить Сергея?**
Потому что на него ссылаются поручения (например, выполненные №101 и №103). Метод TryRemoveMember проверяет все квесты и запрещает удаление, если найден хотя бы один, где Сергей был исполнителем. История не должна вести к удаленному герою

**Ошибка 1 (Занят навсегда):** В IsAssigned убрана проверка статуса. В результате старое выполненное поручение (№101) «держит» героя занятым. Нужно проверять Status == QuestStatus.Assigned
**Ошибка 2 (Сначала назначили, потом спросили):** Проверка IsAssigned стоит после quest.TryAssign(). В итоге квест назначается, но метод возвращает false. Проверка должна быть до вызова
